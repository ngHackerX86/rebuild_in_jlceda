# 验证记录

本页记录**具体版本 + 具体样例**的验证结果，供复核对齐。所有数字来自实际运行，不覆盖未测场景。

> **怎么读这份记录**：每段都标注了它对应的工具版本与 EDA 版本；**不同版本之间的数字不可直接比较**。
> 想复现某一段，请用该段标注的版本，并按文末「复核方式」操作。
> 汇总口径与当前已知差异见 [支持范围与限制](支持范围与限制.md) 第 6 节。

## 记录 2：自动重铺覆铜（2026-11-14 · 工具 0.1.x，EDA 4.1.100）

目的：验证"不靠人手 Shift+B，也能把铺铜算出来"。

| 步骤 | 结果 |
|---|---|
| 导入全新工程（未灌铜）| `pcb_PrimitivePour.getAll() = 4`，`pcb_PrimitivePoured.getAll() = 0` |
| 灌铜前 DRC | Connection Error **34（GND）** |
| 调用 `pour.rebuildCopperRegion()`（4 块依次）| 返回 `{async:true, pourFills:[...]}`，**2.3 秒 / 60 条填充路径** |
| 灌铜后 DRC（未调规则）| Connection Error **消失**，余 43 间距 + 47 物理（规则未应用） |
| 应用 `kicad-min` 后 DRC | Clearance **4**、Physical **0**、Connection **0** |

同日用流水线完整复跑（`--stop-after drc`）：

```
① 生成 .eprj3     完成
② 打包 .epro2     完成
③ 导入账号工作区   完成（uuid 1893cf9e…）
④ 打开工程与 PCB   完成（校验 uuid 一致）
⑤ 对齐设计规则     完成
⑥ 重建覆铜         完成（自动，poured=4，5.1 s）
⑦ DRC 复测         完成（Clearance 4 / Connection 0）
```

### 附带修掉的两个问题

1. **同名工程导致导入静默失败**：账号里已有同名工程时编辑器不新建（`imported=null`）。
   现在流水线用 `KiCad_<板名>_<年月日_时分秒>`（如 `KiCad_C3_20261115_031639`）的唯一名称，并在冲突时明确报错。
2. **打开工程不校验目标**：`openProject` 可能停留在旧工程（实测一次耗时 349 s 且 `opened=false`）。
   现在 `eda_open_project.py` 带 `--expect-uuid` 校验当前工程 UUID，不匹配即失败，流水线随之停止。

### 记录 2 补充：接口探测与降级行为（同日）

| 场景 | 结果 |
|---|---|
| `eda_repour.py --dry-run` | 接口存在；可用方法 `getCopperRegion / rebuildCopperRegion / convertToFill / convertToRegion`，退出码 0 |
| PCB 文档未打开时直接调铺铜 API | 抛 `Cannot read properties of null (reading 'map')`（**不是**返回空数组）→ 现改为先 `openDocument(pcbUuid)` 再重试 |
| `--skip-if-poured` | 已有填充时跳过，输出"跳过重铺" |
| 接口缺失（模拟）| 不执行任何写操作，退出码 3，提示手工 Shift+B + `--repour-confirmed` |

## 记录 3：KiCad 9 工程（2026-11-14 · 工具 0.1.x，EDA 4.1.100）

新增两块 KiCad 9（文件 format `20241229`）测试板，用来验证"旧版本工程能被 KiCad 10 的
`pcbnew` 读出并正确重建"：ESP32C3 四层板（内层铺铜）与 Ducky ESP32-S3 两层板。
拉取方式与完整结果见 [测试工程](测试工程.md)。

要点：

- 两块板都跑通 `①→⑦`，自动重铺分别 3 块 / 2 块，各约 1.4 s；
- 转换后的对象数量与源逐网络核对一致（走线/过孔/焊盘），焊盘数的差值来自"仅钢网窗口 → FILL"；
- **源板自身就有未连接**（KiCad DRC 各 2 项），EDA 同样报出，属如实还原；
- EDA 比 KiCad 多报几条未连接（C3 多 1 个网络、Ducky 多 4 个），**列为待查项**；
- 顺带修掉"同会话切换工程失败"：未保存改动会阻塞 `openProject()`，现在重铺后自动保存、打开前也先保存。

### 记录 3 补充：板框丢失（C3）

| 项 | 修复前 | 修复后 |
|---|---|---|
| 板框 POLY（layer 11）| **0 个**（静默丢失） | 1 个 / 197 点 |
| EDA 读回 bbox | — | (12.30,12.20)–(54.90,57.85) mm，与 KiCad 差 ≤0.05 mm |

根因：`_chain_edges()` 用"1 µm 量化 + 严格相等"串端点，而该板 4 处弧-直边接点相差 4.5 µm。
已改为 10 µm 容差聚类，并增加"多环支持 + 开链兜底 + 失败告警"。

### 记录 3 补充：曲线走线方向错误导致的大量 DRC（C3）

现象：C3 转换后 EDA 报 **Clearance 71**（Track-Track 19 / Track-Via 24 / SMD Pad-Track 12 / Hole-Track 16），
而同一块板在 KiCad 里几乎无告警。

定位：这块板有 **4 条曲线走线（PCB_ARC）**。`arc_points()` 早期只调用 `GetArcMid()`，
而 `PCB_ARC` 类只有 `GetMid()`（`GetArcMid()` 属于 `PCB_SHAPE`）。抛异常后落到"靠顺时针标志猜方向"的兜底，
结果 4 条里有 2 条被画到了圆的另一侧，扫过的区域压到走线/过孔/焊盘。

修法：中点获取改为依次尝试 `GetMid()` → `GetArcMid()`；兜底只在明确 `IsClockwiseArc()` 时翻转。

验证：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 曲线走线离散正确 | 2/4 | **4/4** |
| EDA DRC Clearance | **71** | **0** |
| EDA DRC Connection | 8 | 8（与 KiCad 自身未连接一致） |
| 主样例（KiCad 10）| LINE 397 / VIA 47 / POUR 4 | 同左，未受影响 |

## 复核方式

```powershell
python -m rebuild_in_jlc.pipeline --board <board.kicad_pcb> --check-config
# 注意：CLI 重跑会**重新导入一个新工程**，因此"停在 rules → 手工覆铜 → 重跑加 --repour-confirmed"
# 这条流程**不成立**（那条命令操作的是新工程）。手工覆铜请在 GUI 的同一次流程里确认。
python -m rebuild_in_jlc.pipeline --board <board.kicad_pcb> --name R --out out/r --stop-after rules
# 在 EDA 里对该工程执行「设计 → 重建覆铜」
# 仅当*同一次运行*里已由人工确认覆铜时才用（GUI 会自动带上）；不要用它衔接上一次的停止点
```

失败时把 `out/r/run.json` 与相关 `step_*.log` 一并附上即可定位。

## 连接性专项核对（2026-11-15 · 工具 0.3.0，EDA 4.1.100）

起因：怀疑 USB 口焊盘丢网络。核对方法：新增 `tools/verify_pad_nets.py`，
逐盘比较 **KiCad 的 `pad.GetNetname()`** 与 **生成文件里 `PAD_NET` 记录**。

### 焊盘网络：三块板全部一致

| 板 | 位号 | 焊盘组 | 丢网络 | 网络不一致 | 备注 |
|---|---|---|---|---|---|
| ESP32C3 | 68 | 236 | 0 | 0 | J1 的 `S1` 是 4 个焊盘共号、各自 `unconnected-(J1-SHIELD-PadS1)*`，`PAD_NET` 按焊盘号索引只能保留一个（原设计本就不接，属结构性限制）|
| Ducky | 98 | 335 | 0 | 0 | — |
| ESP32-S3 主样例 | 30 | 159 | 0 | 0 | — |

### 走线几何：转换器没丢，EDA 导入会合并极短段

Ducky 的 `USB_D-` 在 KiCad 有 35 段，生成的 `.epcb2` 里也是 **35 段**（含一段 0.07 mil 的微线段，
坐标 `6233.7865,-3826.3771 → 6233.8568,-3826.3771`）；导入 EDA 后通过 API 读回只有 **34 段**
——少的是那条 0.07 mil 段，属 **EDA 侧合并/忽略**，不是转换丢失。

### DRC 连接性对比

| 板 | KiCad 自己 DRC 的未连接项 | EDA 的连接错误 | 说明 |
|---|---|---|---|
| ESP32-S3 主样例 | — | **0 条**（只有 4 条间距）| 无连接性问题 |
| ESP32C3 | — | 8 条（`/CHIP_EN`×2、`/BOOT`×2、`J1-SHIELD`×4）| `J1-SHIELD` 属原设计不接；其余待查 |
| Ducky | **2 项**（USB_D-、USB_D+ 各一对走线未连）| 12 条（6 网 × 2 项）| KiCad 也认为 USB_D± 有断开 |

EDA 的 DRC 明细（`pcb_Drc.check(true,false,true)`）显示，多出来的 4 个网络报的是
"某个 SMD 焊盘与同网走线互不相连"：

```
Net-(AE1-FEED): SMD Pad L5_2 + Track e1095
SPID          : SMD Pad U2_5 + …
Net-(C19-Pad1): …
Net-(JP1-A)   : …
```

按**焊盘矩形**量这些焊盘到同网最近走线的距离：`AE1.1` ≈ 0.98 mil、`U2.5` ≈ 4.72 mil、
`L3.2` ≈ 34.6 mil。也就是说几何上确实存在间隙，KiCad 的 DRC 未把它算成未连接
（可能依赖焊盘本体/其它判定），EDA 算成未连接。

**结论与待办**：转换未丢对象、未丢网络；这 4 个网络属"两种工具对连通性的判定口径不同"，
需在 EDA 里逐点确认是否要显式补线，暂不通过改几何去"消除 DRC"（此前实测延长端点会引入间距错误）。

## 网络一致性的四个层次（0.4.0 起按此记录）

| 层次 | 验证对象 | 不能推出的结论 |
|---|---|---|
| 生成声明核对 | 源网络 ↔ 生成 `PAD_NET`（逐物理焊盘，含空网络）| 目标焊盘存在、实际导入使用了该映射 |
| 导入实体核对 | 每枚实际焊盘 / 铜图元回读的网络 | 铜几何接触正确、覆铜完整 |
| 几何连通核对 | 铜接触与跨层连接图 | 规则、制造与电气性能满足要求 |
| 指定规则下 DRC | 指定版本 / 规则 / 输入状态 | 源与目标几何等价 |

当前工具覆盖：第 1 层由 `tools/verify_pad_nets.py` 完成（0.4.0 起逐物理焊盘 + 空网络参与）；
第 2 层在合成板上做过 EDA API 回读（同号 `SIGNAL`/空 网络正确）；第 3、4 层无自动化。
